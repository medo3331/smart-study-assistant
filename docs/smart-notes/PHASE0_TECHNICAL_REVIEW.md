## 3. التخزين الحالي (IndexedDB)

- قاعدة واحدة لكل المتصفح: `magicly-notes`، **DB_VERSION = 1**.
- 4 object stores: `notebooks` / `pages` / `pages_backup` / `meta`.
- كل سجل owner-scoped: `ownerId` بـ prefix إجباري (`anon:<uuid>` أو `user:<uid>`) — العزل مضمون على مستوى الـ storage، مش UI.
- المحتوى الرسمي = `persistedSnapshot` (كائن opaque): `{ template, strokes, texts, images }`.
- **الرسومات vectors مش صور** — ده اللي هيخلي تحسين الخط (المرحلة 3) ممكن على مستوى الـ geometry، وده ميزة معمارية أساسية نحتفظ بيها.
- الـ CAS: `idbPutRecordIfNewer` يقارن revision + canonical content **داخل نفس الـ transaction** — قرارات `applied/unchanged/stale/conflict` دقيقة وموحّدة.
- `revision` رتيب مش timestamp — القرار سليم.

## 4. الحفظ والتعارض (PageSession / SaveQueue / Locks)

| الآلية | التقييم |
|---|---|
| **Web Locks** | عقد حصري session-scoped لكل owner: `magicly-notes-writer:<ownerId>`. تبويب واحد كاتب، والباقي read-only، والترقية تلقائية لما الكاتب يسيب. **Fail-closed** لو الـ API مش موجود (لا fallback غير آمن). سليم. |
| **SaveQueue** | single-flight — أقدم draft يتجاهل، آخر snapshot هو اللي بيكتب. سليم. |
| **PageSession** | dirty/saving/saved/error، والـ draft الأحدث **متمسحش أبداً** عند فشل. `close()` best-effort flush + `visibilitychange`/`pagehide` flush في المحرر. سليم. |
| **تعارض revision** | `conflict` = نفس revision بمحتوى مختلف → الـ draft يتحفظ + خطأ معلن. صحيح. |

### ⚠️ الفجوة الوحيدة المكتشفة في الطبقة دي (تنفع المرحلة 1)

> **الـ PageSession موجود ومُختبَر لكن المحرر مش بيستخدمه.**
> `NotebookEditor` بيحفظ مباشرة عبر `repo.savePage(buildPageSave(...))` + مؤقت 600ms، بينما طبقة `PageSession`/`SaveQueue` كاملة قاعدة بتُختبر في `__tests__`. النتيجة عملية سليمة (الـ revision guard في الـ idb بيحمي)، لكن فيه طبقتين لنفس المسؤولية — لازم نوحّد المسار (المحرر يمشي على PageSession) قبل ما نبني أي ميزة حفظ جديدة فوقه.

### التبويبان المفتوحان على نفس الدفتر — السلوك الحالي والكافي

- تاني تبويب يفتح الدفتر = **read-only تلقائياً** (الـ lock مش هيمنه)، ومفيش أي write متعارض ممكن يحصل — ده حسب التصميم.
- لما الكاتب يقفل، التاني **بيترقّى تلقائياً** لـ writer (متصدقش الحاجة بتقفل على read-only للأبد).
- **فجوة UX الوحيدة:** التبويب القارئ مش بيعلن صراحة "التبويب ده بيقرا من تبويب تاني بيحفظ" — chip موجودة بس القراءة تنفع رسالة أوضح.
- **فجوة محتملة ثانية:** طالما التبويبين مفتوحين والكاتب بيعدّل، القارئ مش بيشوف التعديلات الجديدة (مفيش BroadcastChannel sync). مش بلوك للمرحلة 1، لكن لازم يتقرر: إما "القارئ يعتبر لقطة ثابتة" (الحالي) أو live refresh في مرحلة لاحقة.

## 9. التصميم المقترح للمرحلة 3 (تحسين خط اليد) — مخطط تقني فقط

**الواقع المعماري:** الـ strokes vectors + quadratic smoothing + pressure/speed taper أصلاً. كده الـ base جاهز.

**الوضع الأول — Natural Beautify (خوارزمي، مفيش AI):**

```
Input:  Stroke[] (نقاط صفحة + ضغط اختياري)
        ↓
1. Decimation     — إزالة النقاط المتقاربة (RDP أو distance threshold)
2. Smoothing      — Catmull-Rom / Chaikin بدل quadratic — انحناء أنعم بمراحل أقل
3. Straightening  — الـ segments شبه المستقيمة تتسطّب (يكشف قصود اليد)
4. Baseline snap  — سطور متقاربة عمودياً تنضم لخط أساس مشترك (اختياري بمعامل قوة)
5. Spacing        — مسافات الكلمات تتظبط خفيف (مرحلة تانية)
        ↓
Output: Stroke[] جديدة — نفس النموذج، متخزنة جنب الأصل
```

- **الأصل متبقي**: نسخة الـ strokes الأصلية تتخزن في snapshot (مثلاً `originalStrokes`) والنسخة المحسّنة في `strokes` — التبديل بينهم button، والـ undo محفوظ.
- **معاينة قبل الاعتماد**: تُرسم النسخة المُحسّنة جنب الأصل والطالب يوافق أو يلغي.
- كله **offline ومجاني** (بلا AI) — تنفيذ واختبار على عينات حقيقية قبل الاعتماد.

**الوضع الثاني — Professional Handwriting (تحويل لنص):**

- **القرار التقني الأهم:** الـ handwriting recognition للعربي **مفيش حلاً offline مضموناً** في المتصفح. الخيارات:
  1. AI vision عبر `/api/chat` أو موديل vision (موجود في المنصة) — نبعت صورة الصفحة + prompt، ونبني مسار احتمالي. **مش دقيق كفاية للعربي الخطي** حالياً — يحتاج نموذج مختبر.
  2. WebAssembly OCR مكتبة (tesseract.js تدعم العربي لكن جودة الخط اليدوي ضعيفة جداً).
  3. الاستفادة من OCR مدمج في pdf.js؟ **لا — ده للنص المطبوع فقط.**
- **التوصية الصريحة:** المرحلة دي تحتاج **POC منفصل** قبل أي وعد بالميزة. نبدأ بـ: صورة الصفحة (canvas render) → موديل vision بنفس `/api/chat` infrastructure → نص مقترح → شاشة مراجعة واعتماد قبل وضع النص في الصفحة كـ NoteText (يستفيد من كل ميزات النص الجاهزة). الأصل بيحتفظ دايماً.

**ممنوع تقنياً في الوضعين:** تحويل الصفحة لصورة واحدة (بينهي قابلية التعديل والتحديد).
