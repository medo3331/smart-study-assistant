نظام إدارة مراحل التطوير في مستودع Magicly (`smart-study-assistant`).
الهدف: **المشروع نفسه يحتفظ بتاريخ قراراته وتقدمه** — مش ذاكرة المالك.

> **هذه الوثيقة هي نقطة الدخول.** لو بتقرأ ملف واحد، اقرأ ده.

## 2. المستويات الاثنان (AREA vs DEV)

الخلط بين المستويين هو أكبر مصدر للفوضى في المستودع. النظام بيفصلهم عمداً:

### `AREA-xx` — نطاق منتج (Product Area)
نطاق واسع في المنتج. **مش وحدة شغل.** بيقاس بـ"مغطى / جزئي / ناقص" مش خطة.
كل الـ10 نطاقات في `ROADMAP.md` Part 1. **دي خريطة تغطية، مش خطة تنفيذ.**

### `DEV-xx` — مرحلة تطوير (Development Phase)
وحدة شغل **محدودة، قابلة للإغلاق، لها acceptance criteria**.
**واحدة فقط مفتوحة في أي وقت** (Phase Lock). كل DEV لها ملف في `phases/`.

> **ليه الفصل مهم:** 4 نطاقات (AREA-07, 08, 10 و 02) مكتملة فعلاً، و6 نطاقات فيها فجوات متفرقة بأحجام مختلفة جداً (من عمود واحد لجدول بيانات كامل). لو عاملناها "مراحل" كانت كل واحدة هتاخد شغل لأيام غير محدودة والـPhase Lock مش هيقدر يشتغل.

## 3. دورة حياة المرحلة (Lifecycle)

```
Stage A — التهيئة      اقرأ التوثيق + git ← حدّد النطاق ← استرجع أي تقدّم سابق
Stage B — Audit         فحص read-only ← أدلة (file:line) ← الموجود/الناقص/المخاطر
Stage C — الخطة        خطة بمهام (ID + acceptance criteria + استراتيجية اختبار) ← عرضها على المالك
Stage D — التنفيذ      تنفيذ بالترتيب + إكمال المترابط + تحديث التوثيق أثناء الشغل
Stage E — التحقق       typecheck / lint / tests / build / RLS / regression ← حالة واضحة لكل واحد
Stage F — التقرير      تقرير كامل + التوصية
Stage G — الاعتماد     المالك يعتمد / يطلب تعديل / يرفض / يطلب تحقيق
```

**لا تُغلق المرحلة إلا بعد Stage G.**

---

## 4. Phase Lock (قاعدة القفل)

```
لا تُفتح مرحلة جديدة إلا لو:
  (1) كل متطلبات المرحلة الحالية مُنفّذة
  (2) اختبارات التحقق اتشغّلت — والـ failures التقنية اتصلّحت
  (3) تقرير المرحلة اتكتب في phases/
  (4) المالك اعتمد النتيجة

اكتشاف خارج النطاق  ← BLOCKERS.md (مش backlog مخفي)
استثناء: مانع حقيقي لاستكمال المرحلة ← يُوثَّق فوراً ويُحال للمالك

"الإغلاق" مش = "الكود اتكتب"
```

## 5. قواعد تشغيلية (Operational Rules)

| # | القاعدة | السبب |
|---|---|---|
| **R1** | **فرع تطوير نشط واحد** في أي وقت | تاريخ المشروع فيه 190 فرع محلي + 110 remote — الفوضى بتضيّع السياق |
| **R2** | **مرحلة DEV واحدة مفتوحة** | نفس السبب — الـPhase Lock بيقع لو اتفتحت اتنين |
| **R3** | أي شغل جديد ← `BLOCKERS.md` أو `ROADMAP.md` Part 2 كـDEV مستقبلي | ما ينفعش يتعمل شغل غير مسجّل |
| **R4** | **كل تقرير يسجّل `branch` + `HEAD` + `timestamp`** | المستودع بيتغير أثناء الشغل (شوف §6) |
| **R5** | قبل ما تقول "خلصت"، اقرأ الـgit state تاني — لا تثق في التوثيق | التوثيق ممكن يكون قديم |
| **R6** | **لا SQL / Migration / Push / Merge / Deploy بدون موافقة صريحة** | حدود المالك |
| **R7** | **لا حذف ولا نقل ملفات** بدون موافقة صريحة | `git mv` / `rm` لازم موافقة |
| **R8** | استخدم prefix `DEV-##` لمراحل التطوير. **لا تستخدم `P1..Pn`** | `docs/MAGICLLY_STATUS.md` بيحجز `P*` لـP0 tracker القديم |
| **R9** | `AREA-##` لنطاقات المنتج فقط | نفس السبب |
| **R10** | كل حالة اختبار لازم تكون: `PASSED` / `FAILED` / `NOT RUN` / `N/A` | ممنوع ادعاء نجاح لم يُشغَّل |
| **R11** | **ملفات DEV-02 محظورة** — EXTERNALLY OWNED · PROTECTED · TEMPORARILY OUT OF SCOPE | التعديل يجري في جلسة أخرى — حماية كاملة حتى إبلاغ المالك |
| **R12** | **لا SQL / Migration / Commit / Push / Merge / Deploy بدون موافقة صريحة** | حدود المالك — حتى لو الخطوة معروفة أو مقترحة ضمن مرحلة نشطة |

## 6. المستودع بيتغيّر أثناء الشغل — قاعدة تشغيلية

**مش ملاحظة نظرية — ده اتحقق عملياً:**

| الوقت (2026-11-14) | ما حصل |
|---|---|
| ~16:40 | `git status` بيقول: `M app/api/lesson-content/route.ts` + 3 ملفات untracked |
| 15:56:52 | commit `b2ed5606` بيحط نفس الملفات |
| 16:21:38 | `EXAMS_PHASE1_AUDIT.md` يظهر |
| 17:05 | `EXAMS_PHASE2_PROPOSAL.md` يظهر |
| 17:13 | `git status` بيقول الملفين untracked |

⇒ **فيه session تانية شغالة على نفس الفرع.** أي رقم "الحالة الحالية" لازم يبقى مربوط بـ `(branch, HEAD, timestamp)`.
ولذلك: **`ACTIVE_PHASE.md` بيتحدّث في بداية كل session وبعد كل commit.**

## 9. حدود الصلاحية

- لا تنفيذ SQL على الإنتاج (كله manual SQL Editor) بدون موافقة
- لا push / merge / deploy
- لا حذف أو نقل ملفات أو فروع أو worktrees
- لا تعديل وثيقة نظام قائمة (المصدر مرجعي) — اقرأها بس
- لا ادعاء نجاح اختبار ما اشتغلش
- لا تعديل أنظمة غير مرتبطة عشان مرحلة تبان "خلصة"
- لا كسر قرار مقفل (`D-REAL-*` أو `D-DEV-*`) بدون قرار جديد صريح يسجّله المالك
